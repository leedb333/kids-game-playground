# 벽돌깨기: 공 속도 점검과 현재 단계 다시 시작

## 1. 기존 구조와 원인

기존 `stage.speed = 222 + (단계 - 1) × 7`은 의도된 단계별 난이도 차이입니다. 이전 커밋 `406d173`에서 시작 속도 1.2배가 전체 단계에 적용되어 있었습니다. 별도의 8·9단계 전용 속도값이나 저장된 속도값은 없었습니다.

하지만 엔진이 다음 두 값 중 작은 값에 1.2를 곱하고 있었습니다.

1. `stage.speed × 게임판 높이 / 620`
2. `max(90, (패들 높이 위치 - 가장 아래 벽돌 끝 - 공 반지름) / 0.6)`

두 번째 ‘배열별 여유 공간 제한’ 때문에, 같은 화면에서도 아래까지 내려온 8·9단계의 하트/클로버는 크게 느려졌습니다. 짧은 태블릿 화면에서는 두 단계가 같은 제한값으로 낮아지기도 했습니다. 2·3·10단계도 화면 높이에 따라 제한을 받았습니다. 1.2배 설정 누락이나 주사율·저장 데이터의 덮어쓰기 문제는 아니었습니다.

## 2. 1~10단계 점검표

## 3. 수정 방식과 측정

- `src/games/brick-breaker/speed.ts`에서 첫 단계 222, 단계 증가 7, 기존 개선 배수 1.2, 기준 높이 620을 공통 관리합니다.
- 적용 공식: `목표 속력 = 단계 기본값 × 실제 가상 높이 / 620 × 1.2`. 벽돌의 모양·개수·제거 여부는 속력에 영향을 주지 않습니다.
- 발사, 공을 놓친 뒤 재발사, 단계 선택, 저장된 벽돌 판 복원, 화면 크기 변경, 다시 시작이 같은 엔진 생성 규칙을 사용합니다.
- 충돌 후에는 `sqrt(vx² + vy²)`를 목표 속력으로 맞춥니다. 패들은 입사 방향의 수평 성분을 유지하며 수직 성분만 반전하는 대칭 반사를 유지합니다. 벽·벽돌의 지나치게 수평/수직인 방향 보정은 기존대로 유지합니다.
- 10초 후 가속은 없고 두 번째 공이 생기는 기존 규칙을 유지합니다. 두 공의 속력도 같은 목표를 따릅니다.
- 기존부터 실제 프레임 경과 시간을 누적해 1/120초씩 물리를 계산했습니다. 이 구조는 유지했습니다. 긴 정지 후 순간이동을 막는 기존 100ms 경과 시간 제한도 유지합니다.
- 엔진에서 목표값과 `Math.hypot(vx, vy)`를 비교하고, 30·60·90·120·144Hz 및 불규칙한 간격으로 1초 이동한 실제 좌표를 확인했습니다. 300·350·511·620·1200·2000U 높이도 검사했습니다.
- 실제 브라우저의 1280×720 화면에서 10개 단계 모두 발사·일시정지·재개 시 목표/실측 속력의 일치를 검사했습니다. 이때 Stage 8은 268.1421U/s, Stage 9는 275.0682U/s였습니다. 해당 게임판 가로폭 1248px에서 각각 약 334.64px/s, 343.29px/s입니다.
- CSS 픽셀 속력 환산: `U/s × 캔버스 표시 가로폭(px) / 1000`. 단순 프레임당 이동 거리나 화면 픽셀 차이로 추정한 값이 아닙니다.

## 4. 다시 시작 버튼과 확인창

- 태블릿과 가로 스마트폰: 기존 상단 메뉴에 원형 화살표와 **다시 시작** 버튼을 추가했습니다. 메뉴 높이와 게임판 높이는 늘리거나 줄이지 않았습니다.
- 작은 스마트폰: **멈춤 → 다시 시작**으로 들어갑니다. 상단 공간을 더 차지하지 않습니다. 태블릿도 일시정지 메뉴에서 사용할 수 있습니다.
- 확인 문구: **이 단계를 처음부터 다시 시작할까요?** 기본 초점은 취소에 있어 실수로 초기화하지 않도록 했습니다.
- 확인창이 열린 동안 공·물리 시간·입력을 정지합니다. 취소/Escape는 기존 판을 유지하며, 플레이 중 열었으면 플레이를 재개하고 이미 멈춘 상태였다면 멈춘 상태를 유지합니다.
- 확인하면 현재 단계의 일반/황금벽돌 전체, 공 하나의 발사 전 위치, 정지 상태, 패들 중앙, 해당 단계 목표 속력, 10초 타이머, 두 공 모드, 잔상·효과·놓친 횟수를 초기화합니다.
- 화면 회전으로 엔진이 바뀐 상태에서 취소할 때는 기존 화면 회전 안전 동작인 ‘멈춘 뒤 재발사’를 유지합니다.

## 5. 저장 호환성

기존 키 `kids-game-playground:v1:game:bricks:r1`과 `version:1` 형식을 유지합니다. `restartStage()`는 현재 단계 번호와 해당 단계 `boards[id]=[]`만 새로 저장합니다. 완료 단계 목록과 다른 단계의 벽돌 진행은 그대로 복사합니다. 모든 단계를 자유롭게 고르는 기존 방식도 유지합니다.

기존 저장 형식에는 공 속도·위치·진행 시간이 없으므로 예전 속도를 이어받지 않습니다. 기존과 동일하게 제거한 벽돌과 완료 기록을 이어가며, 공은 새 발사 상태에서 시작합니다. 다른 게임의 저장 키에는 접근하지 않습니다.

## 6. 검증 결과

- TypeScript·프로덕션 빌드·Pages 경로 검사: 통과.
- 벽돌깨기 기존 검사 24개 + 새 검사 13개 = **37개 통과**.
- 10개 실제 배열을 정상 발사·패들 조작으로 모두 클리어하는 시뮬레이션도 통과했습니다.
- 황금벽돌 즉시 완료, 마지막 벽돌 완료, 일반 벽돌만 없어지고 황금벽돌은 남은 상태, 다음 단계, 마지막 축하, 두 공, 놓침·재발사, 대칭 반사, 오프라인과 저장 차단 검사를 유지했습니다.
- Stage 1·8·9에서 일부 벽돌이 없어진 저장 판을 열어 취소·초기화·완료 기록/다른 판 보존·저장·홈 복귀 후 이어하기를 확인했습니다.
- 진행 중 취소와 이미 일시정지한 상태에서 취소, 공·패들·타이머 초기화, 반응형 확인창과 48px 이상 버튼, 게임판 높이 보존을 검사했습니다.
- 전체 검사 구성은 기존 184개 + 새 13개 = **197개**입니다. PR의 GitHub 검사에서 다른 다섯 게임을 포함한 전체 회귀 검사를 실행합니다.

실제 갤럭시 기기의 주사율·터치감·성능은 미검증입니다. 화면 크기 모의 검사는 1280×800 / 1280×720 / 360×800 / 320×640 / 800×360의 Chrome에서 수행했습니다. 낮은 성능으로 100ms보다 긴 프레임 정지가 생기는 경우에는 기존 안전 제한이 적용되므로, 모든 성능 환경에서 똑같이 매끄럽다고 단정하지 않습니다.
